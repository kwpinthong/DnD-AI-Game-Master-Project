สัญญากลางระหว่าง frontend กับ backend ของทุกหน้าใน Screens and Flows v2 (GEN-086)

- **frontend** ใช้ type + zod schema จาก `@isekai/protocol` อย่างเดียว ทำงานบน fixture / mock ได้โดยไม่รอ backend (GEN-100) แล้วค่อยต่อของจริงใน GEN-101..103
- **backend** ทุก payload ที่ส่งต้องผ่าน schema ในตาราง (test `apps/server/test/contract.test.ts` ยิง endpoint + socket ของจริงด้วย mock AI แล้ว parse ทุกคำตอบ) งาน backend ใหม่ที่ทำของ **pending** ให้เสร็จ: ส่งตาม schema แล้วเปลี่ยนสถานะเป็น `ready` ใน `packages/protocol/src/contract/registry.ts` แล้วรัน `pnpm --filter @isekai/protocol contract:docs`
- ตารางด้านล่างสร้างจาก registry (test ใน `packages/protocol/test/contract.test.ts` fail ถ้าไม่ตรง) และ test ฝั่ง server fail ถ้า route ที่ server มีไม่อยู่ในตาราง หรือ `ready` ใน registry แต่ server ไม่มี
- fixture ตัวอย่างของทุก schema: `CONTRACT_FIXTURES` ใน `@isekai/protocol/contract`

## กฎของ schema ฝั่งผู้เล่น
- ไม่มี field ตัวเลขของ karma / reputation / affinity / relationship / DC / total / modifier (test `playerNumberLeaks` เดิน schema ทุกตัวที่ผู้เล่นได้รับ) ผู้เล่นได้คำแทน: `conduct` (กรรม 11 ขั้น), `socialTitle`, `bond` (F4 คำ + แถบ 6 ขั้น), `roll.difficulty` (Q-198)
- ข้อยกเว้นเดียว: `GameLogResponse.reveal.players[].karma` ตัวเลขเล็กข้างคำกรรม หลังเกมจบเท่านั้น (Q-196)
- branch `view: 'gm'` ของ `SurroundingsResponse` / `OriginResponse` / `GameTimelineResponse` เป็นของ GM คน ผู้เล่นไม่ได้รับ
- ผู้เล่นได้แค่ `RoomState.submittedCount` + `submitted` ของตัวเอง (Q-195)
- คำความยาก: `difficultyWord(dc)` ปัดหาขั้นที่ใกล้ที่สุด เท่ากันปัดขึ้น (Q-198) / คำความสัมพันธ์: `bondFor(affinity)` — ใช้ฝั่ง server เท่านั้น ตัวเลขไม่ออกจาก server
- Astral Spirit (Q-192) ได้ feed สาธารณะของทุกสถานที่เป็น entry `feed` ปกติ อ่านอย่างเดียว / ลางสังหรณ์ (Q-193) ถึงผู้เล่น 1 คน ≤ 200 ตัว วันละครั้งใน NOCTHERION
- การ์ดผลที่โดน "รับทราบ" เก็บฝั่ง client (ตาม `seq`) ไม่มี endpoint

## field ใหม่ใน schema เดิม
field ที่ server ยังไม่ส่งเป็น optional ทั้งหมด ของเดิมที่ server ส่งอยู่จึงยังผ่าน schema / web ต้องรับกรณีไม่มี field จนกว่า owner ส่ง / ข้อความ client → server ที่ยัง pending (`RoomOmen`) ไม่อยู่ใน `RoomClientMessage` จนกว่า GEN-070 จะรับ (ไม่งั้น server จะถือเป็น action)

`new` ในช่อง task เจ้าของ = ช่องว่าง backend ของงานที่ Done แล้ว (GEN-054 / 055 / 057 / 059 / 060 / 064 / 066) ยังไม่มี task รับ
